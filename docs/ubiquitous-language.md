# Ubiquitous Language

This is the living glossary of the project's agreed vocabulary: the terms the code, docs, UI copy, and tests should use for the same concept. It follows the Domain-Driven Design "Ubiquitous Language" practice — one meaning per term _within a bounded context_, with cross-context collisions flagged as seams rather than silently tolerated.

## How to contribute

- Add a row when a feature introduces a concept or renames an existing one.
- Prefer the identifier actually used in code (a constant, type, or function name) as the term; note user-facing copy that intentionally differs.
- If a term has more than one meaning in different parts of the codebase, keep one row per meaning and mark the collision as a **seam** — do not merge the rows.
- Keep the glossary small. If a term is obvious and unambiguous, it probably does not need a row.
- Link the code identifier in the row when it helps a reader jump to the definition.

## Bounded contexts

### Handoff (BC1)

The handoff lifecycle: a deliberate context pivot via compaction. A staged request is cut at `turn_end` into a boundary (cut + successor + note + notebook discard drafts), the successor continues the run, and the watchdog enforces a pending request until it is called, reset, or the attempt budget is exhausted.

| Term                                       | Meaning (as used in this context)                                                                                | Notes                                                                                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| handoff                                    | The tool, `/handoff` command, and lifecycle for a deliberate context pivot                                       | Same word names the tool (`HANDOFF_TOOL_NAME`), the command, and the module. Avoid the verb form "hand off" in code identifiers                       |
| cut                                        | The compaction boundary: a `SessionEntry` written at `turn_end`, identified by `details.handoffId`               | Always paired with the successor; a cut without its successor fails the handoff                                                                       |
| successor                                  | The post-cut continuation turn                                                                                   | Its message must persist after the cut with no later compaction                                                                                       |
| staged / submitted / declined              | Phases of `StagedHandoff`                                                                                        | "staged" is also used loosely for the whole request slot; a declined request carries a `declineReason` (abort / error / missing result)               |
| nextInstruction                            | The instruction carried into the next context, delivered verbatim                                                | A human `/handoff <direction>` wins; otherwise the model supplies it                                                                                  |
| context                                    | The model-owned situational remainder, distinct from the instruction                                             | Not the pi `ExtensionContext`, and not the context-window usage                                                                                       |
| continuation frame                         | The fixed opening text of the successor turn                                                                     |                                                                                                                                                       |
| discardPages / discardedPages              | The notebook pages drafted (`discardPages`) vs committed (`discardedPages`) for removal with the cut             | Written transactionally as part of the boundary                                                                                                       |
| requested / required                       | The two surface states of the sticky contract                                                                    | "requested" until the context is eligible; "required" once eligible and ready to compact (see `HANDOFF_REQUESTED_STATUS` / `HANDOFF_REQUIRED_STATUS`) |
| eligible                                   | The qualifier deciding whether a pending request is enforceable: context usage at or above ~30k tokens           | `isHandoffEligible` gates both the required status and the readonly boundary promotion                                                                |
| RequestedHandoff / pendingRequestedHandoff | The sticky contract object (state field) covering both requested and required states                             | Known naming debt: the field name covers both surface states — see "requested / required" above                                                       |
| enforcementAttempts                        | Settled runs counted while a handoff is still owed and the eligible nudge was delivered without calling the tool | Budget: `MAX_HANDOFF_ATTEMPTS` (5)                                                                                                                    |
| refusal                                    | A handoff call blocked before executing (not the same as a declined request)                                     | Rules: handoff must be the only tool call in its message; only the first call runs; no call after a failed cut in the same run                        |
| note                                       | The hidden `pi-schematic-handoff-note` message saying the system prompt is stale until the next run starts       |                                                                                                                                                       |
| compaction                                 | The transcript-replacement mechanism; the handoff's cut is a compaction entry                                    | "compaction" is also a pi-level concept; the handoff cut is the specific case                                                                         |
| pivot                                      | The model-facing word for a topic change or handoff recommendation ("a real pivot")                              | Appears in watchdog copy and the system prompt, not in code identifiers                                                                               |

### Notebook (BC2)

The notebook is a branch-scoped working memory: agent-curated named pages persist as session custom entries, head-truncated at a size cap when a write overruns it. A discard is transactional — it drafts both generation markers plus every survivor page so an interrupted discard cannot resurrect removed pages; rehydration rebuilds in-memory state from the active branch.

| Term                   | Meaning (as used in this context)                                                                                                                                                                                                                                                                  | Notes                                                                                                                                                                                                                                                                |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| page / entry           | A named notebook page is stored as a session entry (`customType` `notebook-entry`). "page" is the addressable name (headings, tool copy, `details.entries`); "entry" is the record on the session branch that holds it — multiple entries can record revisions of the same page, newest valid wins | Legacy predecessor `ledger-entry` survives only as a read alias for compatibility (rehydration.ts). Inside the pager module, "page" also means a terminal screenful — a different sense                                                                              |
| subject                | The granularity word for what one page covers ("one subject or subsystem"); "thread" was a synonym, now converged to subject                                                                                                                                                                       | Frames how large a page should be; not a distinct mechanism                                                                                                                                                                                                          |
| work stream            | The ongoing body of work a notebook serves ("this work stream"); pages are work-stream-scoped                                                                                                                                                                                                      | Arises in tool copy and docs                                                                                                                                                                                                                                         |
| generation / epoch     | One value with two names: `state.epoch` counts generations; every written entry and the `notebook-generation` markers carry it. "generation" is the docs/comment-facing word; "epoch" is the on-disk field name carried by `notebook-generation` markers                                           | Sentinel 0 = no committed generation yet (set to 1 on first write). Seam: `childSessionEpoch` (Spawn) is an adjacent but separate counter — keep the names apart                                                                                                     |
| discardEpochWatermark  | Derived high-water mark (max valid observed page/generation epoch) that stops a later discard from reusing epochs staged by an interrupted discard                                                                                                                                                 | Reset only with the whole notebook; deliberately not reset on handoff invalidation                                                                                                                                                                                   |
| clipped / truncation   | One write event surfaced three ways: `clipped` (state flag on the page, echoed as `details.clipped`), `TruncationReport` / "TRUNCATED by …" (write result), and the `[truncated]` TUI badge + the read notice ("truncated at write time")                                                          | The operational word is **truncation**; `clipped` is the state-flag name, also surfaced as `details.clipped`. Do not extend this meaning to inline preview trimming (see preview)                                                                                    |
| preview                | A shortened first-line snapshot of a page: `formatPagePreview` (80-char cap: 77 chars + `...`), reused by the prompt listing                                                                                                                                                                       | Distinct from the 500-character inline page-body preview in the TUI `/notebook` fallback, which is also described as "truncated" — a different kind of trimming. "badge"/"flag" refer to the TUI truncation badge and the clipped-page flag, not standalone concepts |
| survivor / staged      | Discard bookkeeping: survivors are the pages a discard retains; each survivor's copy is staged before the closing generation marker, so an interrupted pass leaves uncommitted copies that must not be treated as committed — the discard watermark prevents them from being resurrected           | Load-bearing in rehydration.ts and its tests                                                                                                                                                                                                                         |
| topic (semantic frame) | `state.activeNotebookTopic`: the current high-level frame steering spawn-vs-handoff choices and watchdog nudges                                                                                                                                                                                    | Human-set topics are authoritative. Seam: distinct from the prompt-section key `schematic_topic`, the TUI status key (`STATUS_KEY_TOPIC`), and the generic word "topic" for a conversation's overall theme (system-prompt prose)                                     |
| topic boundary         | `NotebookTopicBoundaryHint`, queued when the active topic changes; consumed by the readonly handoff bypass and the watchdog nudge                                                                                                                                                                  | Seam: "boundary" alone is overloaded across the repo — see the handoff cut/boundary (BC1) and the readonly bash guard (BC5). Prefer the compound form in prose                                                                                                       |
| rehydration            | Rebuilding notebook state (`notebookPages`, `epoch`, `discardEpochWatermark`) from the active session branch via `reconstructNotebook`                                                                                                                                                             | Seam: "rehydrate/rehydration" is also used for the readonly posture rebuild (BC5) — a different mechanism with its own module (`readonly-rehydration.ts`)                                                                                                            |
| write lock             | Non-reentrant lock serializing notebook writes; reentrant calls throw                                                                                                                                                                                                                              |                                                                                                                                                                                                                                                                      |

### Spawn (BC3)

The spawn lifecycle: a parent delegates a focused subtask to an isolated child session. Without a requested group, the child uses the parent's model and thinking level; cwd, active registered tools, and readonly posture carry over, and each child builds its own notebook tool definitions over shared notebook state. Children cannot spawn grandchildren or handoff. The result reports a route status, an outcome, and usage.

| Term                               | Meaning (as used in this context)                                                                                                                                                                                                                                                            | Notes                                                                                                                                                                              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| child session / child agent        | The isolated run spawned for a focused subtask. "child session" is the agreed term (glossary); "child agent" is an equal-weight variant used across the codebase and docs                                                                                                                    | The TUI label is bare "child"; "sub-agent" was retired as a one-off synonym (README). A child of a child is a prohibited "grandchild" — children cannot spawn                      |
| spawn                              | The tool, registered as `spawn` (spawn/index.ts:737), its lifecycle, and one invocation ("a spawn", "spawn call")                                                                                                                                                                            | No `SPAWN_TOOL_NAME` constant exists — the registration uses the literal name `spawn`. Countable noun: "a completed spawn"/"aborted spawn"                                         |
| inherit / inherited (route status) | `SpawnRouteDetails.status` `"inherited"`: no nonblank group was requested, so the child uses the parent model/thinking. An unknown requested group also uses the parent model but reports `"unknown-fallback"`; either path may carry explicit spawn thinking (SpawnRouteDetails, router.ts) | Distinct from the `"inherit"` thinking sentinel in the Model Groups TUI (BC4) and from general cwd/tools/posture carry-over — see seam below                                       |
| inherit (cwd/tools/posture)        | cwd, active registered tools, and readonly posture carry over to the child; notebook tools are built child-locally over shared state (createNotebookToolDefinitions), not inherited from the parent registry                                                                                 | Descriptions previously said children inherit "shared notebook tools"; fixed to "child-local notebook tools"                                                                       |
| route status                       | The spawn-route classification `inherited` \| `routed` \| `unknown-fallback`, resolved by `resolveSpawnModelRoute`, reused by parent frontmatter model selection (handleModelGroupFrontmatter)                                                                                               | Only `routed`/`unknown-fallback` print a label (`formatSpawnIdentity`); `inherited` prints bare `model • thinking`. The `/model-groups` command manages configuration, not routing |
| outcome (spawn result)             | Final result `SpawnResultDetails.outcome`: `success` \| `aborted` \| `error`. A completed result never carries `running` — that value is renderer live state (`liveOutcome`), not a result outcome                                                                                           | `aborted` carries `isError=true` but the UI overrides via `outcome`; the text reads "Child agent aborted: …"                                                                       |
| liveOutcome                        | Renderer-only field tracking the live child: `running` while streaming; set to `success` after a clean `message_end` (the message ended without failure, not child completion); reset to `running` on the next `message_start`                                                               | "💬 done" appears only in static/non-nested success views; the collapsed nested view prints no status line for success                                                             |
| truncation marker                  | The fixed marker appended to a truncated child result: `[Result truncated to 2000 lines / 50 KiB (51200 bytes). …]` — always names both caps even if one triggered                                                                                                                           | Notebook analog (BC2): operational word is truncation; `clipped` is the notebook state-flag name, with `[truncated]`/`TRUNCATED by …` as surface text                              |
| epoch (childSessionEpoch)          | `state.childSessionEpoch` is a generation counter bumped on /new; when a child's captured epoch no longer matches, execution treats the run as invalidated (result is `error`; `abortAndInvalidate`)                                                                                         | Seam: this is a separate counter from the notebook epoch (BC2) — keep the names apart                                                                                              |
| stale (renderer reason)            | `getStaleSessionReason` returns `"epoch"` \| `"completion"` \| `"replacement"` to decide whether the attached session is stale for rendering; all three suppress events and rebuild the display — none initiates an abort                                                                    | Seam: the same word "stale" also names the epoch-invalidation sense above; only epoch invalidation can abort a run, renderer staleness only rebuilds views                         |
| childSessions                      | The published child sessions keyed by toolCallId; `executeSpawn` publishes, `renderSpawnResult` claims via get+delete. This is the render delivery queue, not the full live registry                                                                                                         | "claim" removes the entry from this map                                                                                                                                            |
| liveChildSessions                  | All live child sessions including claimed ones, keyed by toolCallId; never replaced (only `.clear()` on reset/teardown). Execution still disposes the session on completion after the renderer attaches                                                                                      | "ownership" senses: registry-slot tracking (generation counter) vs renderer attachment (claim) — keep them apart                                                                   |
| retained child / nested spawn      | `NestedAgentSessionComponent` renders an ordinary child live in the TUI and can retain the view after execution disposes the session; "retained child" is the completed-view case                                                                                                            | "nested spawn" is the code/test name for that component (spawn-event/spawn-render); it is not a grandchild (children cannot spawn)                                                 |
| cancel / aborted                   | Pi's `bashExecution` message field is `cancelled?: boolean` (comments say "cancelled"); the spawn outcome value and user-facing text use "aborted"                                                                                                                                           | Seam: field spelling vs outcome vocabulary — keep "aborted" for outcomes; "cancelled" is the message-flag name                                                                     |
| authority                          | Under `state.readonlyEnabled`, a child shows "You inherit readonly authority in this session." (readonly child note) and gets restricted tools; the spawn prompt guidelines also say children have "the same authority as the parent" — trust guidance, not identical tools or permissions   | Listed in the BC3 term inventory; keep both claims distinct until a single authority model is agreed                                                                               |

### Model Groups (BC4)

A Model Group maps a semantic role to a pool of provider/model entries, with an optional constraint envelope that shapes what spawned children may demand. Groups resolve to a validated snapshot; the modality constraint drives the group's advertised capability set and its ceilings.

| Term                                | Meaning (as used in this context)                                                                                                                                                                                                                                                                                                                               | Notes                                                                                                                                                                                                                                                     |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model Group / model group           | A named set of provider/model entries plus an optional constraint envelope (`ModelGroupDef`, `createGroup`); "Model Groups" is the user-facing plural, "model group" the prose form                                                                                                                                                                             | Orthography variance only — same concept. A group resolves to a validated `ResolvedModelGroup` snapshot                                                                                                                                                   |
| modality                            | One capability in the advertised set: `text`, `image`, or `reasoning`. Derived per member as `model.input` ∪ (`reasoning` when `model.reasoning`), then narrowed by the group                                                                                                                                                                                   | Not pi-ai's "input modality": `reasoning` is a synthetic, model-derived member. "media"/"capability" also appear in UI copy — keep "modality" as the term (singular capability, not the set)                                                              |
| supported / common / effective      | Three distinct sets per group: `supported` = union of member modalities; `common` = intersection (collapses to `[]` when any member is unresolved — diagnostic `empty-common`); `evaluation.effective` = the post-override set (defaults to `supported`, with `text` always kept when supported); `evaluation.aggregate.effective` is still `common` and unused | UI reads "Supported by every model" for `common`, "Automatic — using every capability its members support" for `supported`; the descriptor's `Automatic (${common})` label never renders (toggle rows only), so every visible "Automatic" means the union |
| constraint envelope (group config)  | `ModelGroupDef.constraints`: a v2 keyed envelope retaining unknown keys opaquely; each value is a raw constraint value (e.g. `modalities: ["image"]`)                                                                                                                                                                                                           | Distinct from the spawn constraint envelope — group config stores raw arrays, not requirement wrappers                                                                                                                                                    |
| requirement (spawn arg)             | The spawn `constraints` argument (`SpawnConstraintRequirements`): envelope keyed by descriptor name, each value a `requirement` (e.g. `modalities: {required: ["image"]}`); unknown keys are rejected before a child is created                                                                                                                                 | "Unknown spawn constraint requirement"; "cannot satisfy constraint requirements". Envelope vs item naming persists                                                                                                                                        |
| required (declared)                 | The `{required: [...]}` array in a requirement schema: the declared set of capabilities a spawn must satisfy                                                                                                                                                                                                                                                    | The TUI also prints `text [required]` for the always-present base capability — see seam below. Cross-ref the handoff `requested/required` status (BC1) — same lexeme, different concepts                                                                  |
| required (base capability)          | The TUI label `text [required]` marks text as an always-present base capability (not toggleable) when members support it                                                                                                                                                                                                                                        | Same lexeme as the declared-requirement `required` key — different concepts, same word                                                                                                                                                                    |
| capability ceiling                  | The explicit, subtractive override on a group's modality set (`groupCapabilityCeilings`); the modality descriptor emits a child notice "## Model Group capability ceiling" only when supported image input is excluded by the override                                                                                                                          | TUI state label "Override" and status "media limited to …" name the same concept; "Override" is the canonical state label                                                                                                                                 |
| shadowed-by-project                 | A global group hidden by a same-name project group; flagged `shadowedByProject` and tagged "project override"; `overrideCount` counts such groups in the boot summary                                                                                                                                                                                           | Distinct from constraint override — it is a name-collision state                                                                                                                                                                                          |
| otherScopeHasOverride               | After deleting a group, true when a same-name entry exists in either other scope (project or global), not necessarily a project override                                                                                                                                                                                                                        | Unused by the TUI, which recomputes `otherScope`; a distinct seam (flag for deletion decisions)                                                                                                                                                           |
| scope / policy                      | `scope` (`global`\|`project`) is the placement, user-visible ("Location: project/global"); `policy` (`global-project`/`global-only`) is an access mode: global-only rejects project access and hides the project editor choice                                                                                                                                  | Seam: `ConstraintViolation.scope` is a different `scope` (`group`\|`model`) — keep the two meanings apart                                                                                                                                                 |
| resolved group / ResolvedModelGroup | The validated snapshot produced by `listResolvedModelGroups`: every configured member retained, availability recorded in `validation.unavailableRefs` (`degraded` when only some are unavailable), constraints evaluated into `evaluations` with diagnostics, plus the legacy `modalities` projection                                                           | `evaluations` is the preferred ordered descriptor source; `modalities` remains a fallback projection (prompt, editor summary), not a removed one                                                                                                          |
| usable / available / authenticated  | One predicate, three wordings: `isUsableModel` (registry presence plus configured auth), TUI "available/unavailable", error "no configured/authenticated usable models"                                                                                                                                                                                         | Seam: `usable` in code, `available` in UI, `authenticated` in error text — same predicate; "authenticated" is error copy for configured auth, not proof of a successful auth round-trip                                                                   |
| degraded                            | A group where some but not all members are unavailable; TUI tag "⚠ degraded"                                                                                                                                                                                                                                                                                    | Distinct from "unavailable" (all members) and "available" (none); not in the audit glossary, kept as a real validation state                                                                                                                              |
| stale (modality override)           | A modality override listing modalities no supported member has; boot summary `staleModalityOverrideCount` + TUI tag "⚠ stale modality override: …"                                                                                                                                                                                                              | Surface of the `unsupported-override` diagnostic. Distinct from BC3 renderer/epoch staleness — keep the BCs apart                                                                                                                                         |
| satisfaction                        | The constraint verdict family `ConstraintSatisfaction` (`satisfied`/`missing`), surfaced in errors as "cannot satisfy required modalities"                                                                                                                                                                                                                      | Core verb family across constraints; "satisfy/satisfaction" is the verdict vocabulary                                                                                                                                                                     |
| inherit (thinking level)            | The TUI thinking sentinel `"inherit"` when a member entry has no `thinkingLevel`: use the parent's thinking, clamped to the selected model (BC3 route `inherited`/`unknown-fallback` can also carry explicit spawn thinking)                                                                                                                                    | Cross-ref BC3 `inherit / inherited` rows — same word, different mechanism (thinking sentinel vs route status)                                                                                                                                             |
| frontmatter model-group             | `model-group` frontmatter resolves via `resolveSpawnModelRoute` (no constraints) and applies both model and thinking to the current session; an unknown group reports an error rather than spawning an inherited child                                                                                                                                          | Cross-ref BC3 `route status`; it is session-model selection, not spawn routing (though architecture.md calls it routing)                                                                                                                                  |

### Readonly (BC5)

Readonly is a session research posture: when active, write/edit/powershell are blocked at the tool boundary, and bash commands run behind a command-pattern classifier gate and under an OS sandbox where one is available. A handoff is allowed through only via an explicit `/handoff` or an eligible human topic boundary.

| Term                              | Meaning (as used in this context)                                                                                                                                                                                                                                                                                                         | Notes                                                                                                                                                                                                                |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| readonly / posture                | The session research posture (`readonlyEnabled` in `state.ts`): ON/OFF, toggled via `/readonly` or Ctrl+Shift+R, or set at start by `--readonly` (fallback when no persisted entry exists) or `readonly: true\|false` frontmatter. Explicitly a coding guardrail, not a hardened security boundary                                        | "posture" is the doc/comment-facing word; the TUI label is bare "🔒 readonly". The legacy spelling "read-only" survives only in CHANGELOG and as an OS errno/bwrap term ("read-only file system") — not this concept |
| L1 / L2                           | Code-side layer labels: **L1** = OS sandbox wrapping (`sandbox-exec` on macOS, `bwrap` on Linux) when `canUseOsSandbox()`; **L2** = command-pattern classifier-only path (the only enforcement on Windows). The classifier runs first in BOTH paths as a pre-gate, blocking unsafe commands before any wrapping                           | Docs describe the same stack as "two-layer guard" / "classifier secondary" / "classifier-only" without these labels (architecture.md, README). Non-string input is rejected before either branch                     |
| temp dir                          | The canonical (symlink-resolved) OS temp dir, one shared constant `TEMP_DIR` so the classifier and the sandbox agree on the same reference path                                                                                                                                                                                           | `getCanonicalTempDir` (os-sandbox.ts) re-resolves the same canonical value. The classifier and the sandbox profile may disagree on which paths are writable (#129)                                                   |
| verdict (classifier)              | `Verdict{ok}` (module-private type) — the boolean outcome of `classifyBashCommand`: ok, or a reason                                                                                                                                                                                                                                       | Tests name the classifier result "verdict" (notifications.test.ts)                                                                                                                                                   |
| verdict (guard result)            | `ReadonlyBashGuardResult{action: "allow" \| "block" \| "sandbox"}` — the final decision returned by `applyReadonlyBashGuard`, named `result` at its use sites                                                                                                                                                                             | The DDD audit glossary used "verdict" as an umbrella for this shape; that label is audit-only, not code usage                                                                                                        |
| bypass (frontmatter shortcut)     | `READONLY_BYPASS_COMMANDS = {readonly, notebook, handoff}` — builtin slash-commands skipped from frontmatter preflight at input (index.ts), covering both readonly and model-selection resolution                                                                                                                                         | Seam: unrelated to the other two bypass senses below — the same word carries three meanings within the feature                                                                                                       |
| bypass (handoff policy exception) | The temporary exception that lets handoff run in readonly: explicit `/handoff` or an eligible human topic boundary. UI copy prefers "exception" ("temporary handoff exception"); model-facing copy also says "temporary bypass"                                                                                                           | See `READONLY_HANDOFF_TRIGGER`                                                                                                                                                                                       |
| bypass (classifier evasion)       | Documented ways a command evades the pattern classifier: interpreters with programmatic code (`node -e`, …) and xargs with stdin-fed package managers; mitigated by the L1 OS sandbox where available (readonly-bash.ts header)                                                                                                           | Not a feature — a limitation note                                                                                                                                                                                    |
| promotion                         | Upgrading an eligible human-set topic boundary into a handoff bypass: `canPromoteBoundary` gates on `isHandoffEligible`; `promoteBoundary` (called only behind that gate) creates the pending request. `discardNonHumanBoundary` drops non-human boundaries; `markBoundaryAdvisory` marks an ineligible human boundary as already advised | The promote path is the only eligibility-gated action; the discard/advisory helpers run before/without the gate                                                                                                      |
| sandboxedBashCallIds              | In-flight sandboxed bash `toolCallId`s tracked in state so a denial notice can be appended to the failed tool result (index.ts `tool_result` hook)                                                                                                                                                                                        | The child spawn path tracks the same fact locally via `record.sandboxed`                                                                                                                                             |
| posture summaries                 | Shared copy consts in notifications.ts for the ON/OFF/handoff-exception states (`READONLY_ACTIVE_SUMMARY`, `READONLY_DISABLED_SUMMARY`, `READONLY_HANDOFF_EXCEPTION_SUMMARY`, …). Some are model-facing custom messages sent with `display: false`; the TUI toggle notification uses `READONLY_ENABLED_STATUS`                            | "exception" (UI) vs "bypass" (code/model-facing) split mirrors the bypass seam                                                                                                                                       |
| denial phrase                     | Case-insensitive lowercase comparison strings used to detect a likely blocked write: `SANDBOX_DENIAL_PHRASES` — "operation not permitted" (darwin), "read-only file system" (linux)                                                                                                                                                       | A match is a hint taken from command output, not proof of a denial (output can contain the phrase without one)                                                                                                       |
| scope (readonly)                  | The statement of what readonly blocks: `READONLY_BASH_SCOPE` ("bash writes/deletions outside temp blocked") and `READONLY_NON_TEMP_MUTATION_SCOPE`                                                                                                                                                                                        | Policy summaries, not exhaustive enforcement rules. Seam: distinct from BC4 constraint `scope` (`group`\|`model`) and placement `scope` (global/project)                                                             |
| rehydration (readonly)            | Rebuilding the readonly posture from branch state: `rehydrateReadonlyState` (index.ts), using `readonly-rehydration.ts` for the branch lookup                                                                                                                                                                                             | Seam: a different mechanism from BC2 notebook rehydration                                                                                                                                                            |

### Advisory steering (BC6)

The watchdog is an advisory layer over handoff/readonly: band-throttled nudge messages help the model keep context fresh, and a required-handoff budget is enforced by counting settled runs that received the eligible nudge without calling the tool.

| Term                 | Meaning (as used in this context)                                                                                                                                                                                                                   | Notes                                                                                                                                                                                                            |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| primacy zone         | The first ~30% of the context window, the region the model uses well. Implemented as a `percent < 30` gate in the context hook; the zone itself is never computed                                                                                   | Hyphen variant "primacy-zone" appears in comments/copy. This percent gate is independent of handoff token eligibility (`MIN_HANDOFF_TOKENS = 30_000`) — two unrelated "30" thresholds                            |
| band                 | The context-percentage throttle band: null (<30%), 0 (30–49%), 1 (50–69%), 2 (70+%), stored in `lastWatchdogBand`. A nudge fires only when crossing into a higher band (and not at all while a handoff/boundary is pending)                         | Docs/tests call these "pressure bands", "practical pressure bands", "Band thresholds". Band (interval) vs threshold (boundary): keep apart                                                                       |
| nudge                | An advisory custom context message injected by the `context` hook: `pi-schematic-watchdog` (band-gated) and the one-shot readonly toggle `pi-schematic-readonly-nudge`                                                                              | Module-header comments, docs, and test helpers historically say "reminder"; model-facing copy includes "Topic-aware context reminder."; the cancel path uses a UI notification — one family, three surface words |
| attempt counting     | A settled run counts against the handoff budget only if the eligible nudge was delivered and the tool was not called (`settleCountsAttempt`: `!toolCalled && eligibleNudgeDelivered`); `MAX_HANDOFF_ATTEMPTS` (5). Cross-ref BC1 requested/required | Comments say "enforcement budget", tests "cancellation budget"; user copy says "cancelled after 5 attempts"                                                                                                      |
| advisory             | State flag `advisoryDelivered` / `markBoundaryAdvisory`: an ineligible human topic boundary stays advisory (guidance, not enforcement) until context is eligible                                                                                    | Distinct from promotion (BC5), which activates the handoff bypass                                                                                                                                                |
| task-boundary signal | The model-facing phrase "strong task-boundary signal" for the same concept as the type `NotebookTopicBoundaryHint` and the state comment "Boundary cue"                                                                                             | One concept, three surface words                                                                                                                                                                                 |
